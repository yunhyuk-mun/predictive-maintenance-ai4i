# 예측에서 조치로: 조치 설계 v1.1 (2026-10 추가)

원래 노트북은 고장 확률을 계산하는 데서 끝났다(재현율 79%). 다시 보니 테스트셋 알림 96건 중 41건이 헛알림이었고, 알림을 받은 사람이 무엇을 할지가 정해져 있지 않았다. 이 폴더는 문제를 **"더 정확한 모델"에서 "알림을 받은 사람이 무엇을 하는가"로 다시 정의**하고, 그 구조를 시간축이 있는 데이터에서 시험한 기록이다.

> 두 데이터 모두 **합성 데이터**다. 아래 수치는 구조와 방법을 보여 줄 뿐, 실제 설비에서의 효과 크기가 아니다.

## 1. AI4I 2020: 물리 파생변수와 조치 설계

`ai4i_action_design.py` · 원본 노트북과 같은 설정 · 10회 분할 평균 · 임계값 0.5

| 입력 | 찾음 | 놓침 | 헛알림 |
|---|---:|---:|---:|
| 기존 5개 센서 | 53.8 | 14.2 | 35.3 |
| + Type(L/M/H) | 53.7 | 14.3 | 36.3 |
| + 온도차, 출력(토크×각속도), 마모×토크 | 55.9 | 12.1 | 23.0 |
| + Type + 물리 파생 | 55.7 | 12.3 | 19.0 |

- 고장이 "두 값의 관계"(온도차, 출력)로 정해지는 경우, 그 관계를 변수로 직접 넣으면 헛알림이 줄었다. RandomForest로 바꿔도 같은 방향이었다(45.8 → 28.9).
- Type 단독 효과는 없었다. 분할 1회에서 보인 개선(41 → 28)은 착시였다.
- 남은 놓침의 59%(73/123)는 공구 마모 고장(TWF)이다. 이 유형은 마모 200~240분에서 무작위로 발생해 순간 상태로는 맞히기 어렵다.

**조치 설계 v1.1**

| 항목 | 결정 |
|---|---|
| 높음: 확률 ≥ 0.5 + 물리 조건 | 즉시 점검. 열 방출·출력 조건은 엔지니어 직행 + 작업자 동시 통보, 그 외는 작업자 먼저 |
| 중간: 확률 ≥ 0.3 | 사람 호출 없이 기록 + 다음 PM 목록 |
| 공구 마모 ≥ 200분 | 알림이 아닌 공구 수명 관리(계획 교체) |
| 점검 기록 | 이상 확인 / 예방 조치 / 이상 없음. 기준 조정에는 "이상 확인"만, 20건 이상 쌓인 뒤 |

시뮬레이션에서 중간 단계 알림은 93%가 헛알림이었다(23.9건 중 1.6건). 확률 하나로 만든 중간 구간에 사람을 부르면 안 된다는 근거로 썼다.

**한계**
- 물리 조건이 곧 이 데이터의 고장 생성 규칙이다. 조건만으로 고장 339건 중 330건을 잡는다. 높음 단계 정밀도(0.83)는 이 때문에 부풀려져 있다.
- 같은 점검 건수(약 209건)로 맞추면 임계값만 낮춘 경우(놓침 5.2)와 정책(놓침 4.0)의 차이는 약 1건이다. 정책의 가치는 숫자가 아니라 역할 분담 구조에 있다.
- 행이 독립된 순간 기록이라 시간 여유(리드타임)를 말할 수 없다.

## 2. Azure Predictive Maintenance: 시간축·설비·정비 기록이 있는 데이터

`azure_pdm_v11.py`, `azure_pdm_checks.py` · [Kaggle 데이터](https://www.kaggle.com/datasets/arnabbiswas1/microsoft-azure-predictive-maintenance) · 설비 100대, 2015년 시간별 기록
설정: 3시간 간격 스냅샷, 라벨 = 24시간 안에 고장, 시간 분할(학습 ~7월 / 기준 결정 8월 / 테스트 9~12월)

| 방법 (테스트 9~12월) | PR-AUC |
|---|---:|
| 규칙: 최근 24시간 오류가 있으면 알림 | 0.46 |
| 모델: 센서만 | 0.29 |
| 모델: 센서 + 부품 교체 후 경과일 | 0.92 |
| 모델: 전체 (오류 기록 포함) | 0.999 |

- **0.999는 성능이 아니라 생성기의 흔적이다.** 고장 761건 중 685건은 마지막 오류가 정확히 24.0시간 전에 기록돼 있고, 오류 종류가 부품에 1:1로 묶여 있다.
- 남는 관찰: 센서만으로는 약했고, **정비 기록(부품 교체 후 경과일)을 넣자 크게 좋아졌다.** 조치 기록이 다시 판단의 입력이 되는 구조가 필요한 이유다. 다만 이것도 생성 규칙("교체 직후 고장 억제")을 반영했을 수 있다.
- 점검 결과 3분류(센서 + 교체 이력 모델): 이상 확인 224 / 예방 조치 28 / 이상 없음 11. "예방 조치"는 마침 예정 정비가 있었다는 뜻일 뿐, 알림이 정비를 이끌었다는 근거는 아니다.

**점검**

| 점검 | 결과 |
|---|---|
| 라벨 섞기(누수) | PR-AUC 0.013 → 누수 없음 |
| 처음 보는 설비 30대 | 0.95 |
| 기간 3개 변경 | 0.90~0.93 |
| 시드 3개 변경 | 0.92~0.93 |

## 3. 정리
- 확인한 것: 도메인 지식으로 만든 변수가 헛알림을 줄인다. 모델로 못 잡는 고장은 정비 기준이 맡아야 한다. 정비 기록은 센서만큼, 혹은 그보다 중요한 데이터다.
- 확인하지 못한 것: 실제 설비에서의 효과 크기, 알림이 실제로 고장을 막았는지.
- 다음: 실제 센서 데이터로 같은 구조(알림 → 점검 → 결과 기록 → 기준 조정)를 돌려 보기.

## AI 활용
코드 작성, 분석, 검증(독립 재현·비판 검토)은 AI 코딩 에이전트(Claude Code)로 수행했다. 문제 재정의, 조치 설계의 결정 사항, 결과 채택과 추가 검증 요청은 작성자가 판단했다.
